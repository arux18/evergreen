# Reversibility

**Category:** Generative UI — Control  
**Layer:** Interaction / State Management  
**Status:** Emerging law — generative UI specific

---

## Definition

Every generative interaction must provide a clear path back. Because AI-generated UI feels stateless to users — there is no obvious history, no visible diff, no prior version sitting in memory — undo, reset, and version awareness are structural UX requirements, not optional enhancements.

---

## Core Principle

Static interfaces have explicit state — a form field has a value, a toggle is on or off, a modal is open or closed. Users understand what changed because they caused the change directly.

Generative interfaces obscure state. The AI produces output and the user receives it, but there is no tactile sense of "what was there before." This creates two risks:

1. **Irreversibility anxiety** — users are afraid to interact because they can't undo
2. **Loss of context** — users can't remember or recover a previous output that was more useful

Reversibility design solves both by making prior states accessible and making the path back visible.

---

## The Three Types of Reversibility

### 1. Micro-reversibility — within a generation
Ability to stop, interrupt, or modify generation while it's in progress.

**Patterns:**
- "Stop generating" button that appears during active generation
- Ability to edit the prompt mid-generation and restart
- Partial output is preserved with a clear truncation marker if stopped

### 2. Session reversibility — within a conversation or session
Ability to return to a previous generated state within the current session.

**Patterns:**
- Conversation/thread history that persists in the sidebar
- "Previous version" or "show earlier response" affordance on generated content
- Regenerate button that produces a new version while the prior one is still accessible

### 3. Configuration reversibility — across sessions
Ability to return to a known-good state or default configuration.

**Patterns:**
- "Reset to defaults" for user-configured generative parameters
- Saved states or bookmarked configurations
- A visible record of what inputs produced what outputs

---

## Design Decisions

### Surface reversibility at the point of completion
The moment generation ends is when the user most needs to see their options. The completion state should include:
- A regenerate affordance ("try again" / "get another version")
- A reference to the prior state if one exists ("back to previous")
- An edit affordance that returns to input without destroying the output

### Don't require reversibility to be discovered
Undo paths must be visible — not hidden in menus, not keyboard-shortcut-only. Users in a generative interface are already in unfamiliar territory. Reversibility should feel like a first-class citizen of the UI.

### Preserve, don't replace
When generating a new version of something, show the new version *alongside* or *after* the prior one — don't silently replace it. Users should be able to compare versions before committing to one.

### Distinguish "undo" from "start over"
- **Undo** — returns to the immediately prior state (last version of this output)
- **Start over** — clears the canvas and returns to the idle state

These are different actions with different stakes. They need different affordances and different confirmation patterns.

---

## Edge Cases to Design For

| Scenario | Reversibility Behavior |
|---|---|
| User doesn't like the generated output | "Regenerate" produces a new version; prior version remains visible |
| User accidentally clears the canvas | Confirmation required before clearing; recent output recoverable |
| User wants to try a different prompt | Edit input without losing current output; new output appears below or alongside |
| Session ends / page refreshes | Session history persists; user can return to prior state |
| Generation fails mid-stream | Partial output preserved with truncation marker; retry affordance visible |
| User returns after days away | Prior sessions accessible in history; no cold-start penalty |

---

## Evergreen Application

- Financial projections generated by Evergreen Intelligence carry high stakes — users need to compare scenarios, not just receive one answer. "Show me this alongside my previous projection" is a core use case, not an edge case.
- Retirement calculator outputs should never silently replace a prior calculation — always preserve the prior state for comparison
- The `.pencil` UX rules should specify: generated financial content is never destructively replaced
- Consider a lightweight "scenario history" pattern in the sidebar — users can return to any prior generated scenario within a session
- "Reset to my baseline" is a critical affordance for HNW clients who may have iterated through many AI-suggested scenarios

## Related Laws

- **Output Anchoring** — persistent controls (Layer 2) are the primary home for reversibility affordances
- **Intentional Seams** — seams are where regenerate and edit affordances live
- **Legible Generation** — the completion state is when reversibility affordances surface
- **Graceful Degradation** — partial output recovery is a reversibility concern

---

## Anti-Patterns

- Silently replacing generated output when a new version is requested
- Requiring keyboard shortcuts (Cmd+Z) as the only undo mechanism
- Clearing the canvas without confirmation
- No "stop generating" affordance during active generation
- Session history that disappears on page refresh
- Regenerate that produces a new version with no reference to the prior one
- A single "start over" that conflates undo with full reset
